# AGENTS.md — правила разработки «Моей истории»

## Роль

Ты — AI coding agent, работающий над MVP веб-продукта «Моя история».

## Главный принцип

Реализуй существующую продуктовую и визуальную спецификацию. Не придумывай новый продукт.

Перед реализацией любой заметной функции прочитай:
1. `PRD.md`
2. `VISUAL-DESIGN.md`
3. `COMPONENT-SPEC.md`

## Жёсткие ограничения MVP

1. В одной memory card может быть только **одна фотография**.
2. Видео в MVP нет.
3. Не добавлять multiple upload, галереи или коллажи.
4. Не добавлять AI-функции без отдельного требования.
5. Не добавлять sharing, PDF export или социальные функции без отдельного требования.
6. Не добавлять XP, badges, medals, streaks или другую игровую механику.
7. Не показывать проценты заполнения.
8. Не превращать интерфейс в dashboard/SaaS.
9. Не добавлять кнопку `Готово` для обычного редактирования — изменения должны сохраняться автоматически.
10. Не показывать пользователю выбор aspect ratio при crop.
11. Не заменять большой полупрозрачный `+` стандартной кнопкой `Добавить фото`.
12. Не удалять карточку только потому, что фотография удалена.

## Приоритеты

Если есть конфликт:
1. безопасность/корректность;
2. PRD;
3. Visual Design Specification;
4. Component Specification;
5. существующая архитектура проекта;
6. удобство реализации.

Не менять продуктовые решения самостоятельно. Если обнаружено противоречие между требованиями, остановись и сообщи о нём пользователю.

## UX

Пользователь должен чувствовать, что он собирает историю своей жизни, а не заполняет приложение.

Пустое состояние не должно выглядеть как ошибка или незавершённая задача.

Фотографии являются главным визуальным элементом.

## Визуальный стиль

Использовать направление `Warm Editorial / Human Memory`:
- тёплый светлый paper/ivory фон;
- спокойная приглушённая палитра;
- качественная кириллица;
- editorial typography;
- мягкие тени;
- умеренные радиусы;
- минимум декоративного UI;
- обычные пользовательские фотографии должны выглядеть естественно.

Не использовать:
- glassmorphism как основной стиль;
- неон;
- чрезмерные градиенты;
- игровые эффекты;
- тяжёлые dashboard cards;
- чрезмерный luxury/glamour.

## Код

Пиши простой, поддерживаемый код.

Не создавай преждевременную сложную архитектуру.

Не добавляй зависимости без необходимости.

Переиспользуй компоненты.

Сохраняй типизацию, если выбранный стек её поддерживает.

## Работа с изменениями

Перед крупным изменением:
- проверь существующий код;
- найди затрагиваемые компоненты;
- не переписывай проект целиком без необходимости.

После изменения:
- запусти доступные lint/typecheck/test/build команды;
- исправь очевидные ошибки;
- проверь responsive behavior.

## Работа с пользователем

Не проси пользователя писать код, если задачу может выполнить агент.

Если нужна информация, которой нет в спецификации, задай конкретный вопрос.

Не утверждай, что функция реализована, пока она не проверена.

## Definition of Done

Функция считается готовой, когда:
- соответствует PRD;
- соответствует visual design;
- соответствует component behavior;
- работает на mobile и desktop в пределах спецификации;
- нет очевидных console/build/type ошибок;
- accessibility basics соблюдены;
- не добавлена лишняя функциональность.
